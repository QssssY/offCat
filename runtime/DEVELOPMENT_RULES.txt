项目开发统一执行约束

一、总原则

1. 所有开发必须严格基于当前项目已有结构继续实现，禁止脱离现有项目重做。
2. 所有开发必须遵守当前版本规划、阶段边界和功能顺序，禁止跳过当前功能直接开发后续功能。
3. 每一轮只允许完成一个已指定功能；当前功能完成后必须停止，等待验收，不得擅自继续下一个功能。
4. 禁止擅自扩展范围，不得自行增加未明确要求的功能、页面、数据结构或产品模块。
5. 实现方案必须优先选择最小可行、最小增量、最小风险方案，避免过度设计。

二、开发前检查要求

1. 开始编码前，必须先读取最新的 task 文件和 stage 文件，确认当前版本进度、已完成功能、当前待开发功能及阶段边界，不得擅自跳过或重复开发。
2. 每次修改文件前，必须先读取该文件的最新内容，确认当前实现状态，不得基于记忆或猜测直接覆盖。
3. 开始编码前，必须先检查并沿用项目现有规范，包括但不限于：
- 项目目录结构
- 前后端命名风格
- DTO / Entity / Mapper / Service 命名方式
- 数据库表和字段命名方式
- task 文件的生成方式
- stage 文件的维护方式
- 现有 AI 调用封装方式
- 现有代码注释风格
4. 如果项目中已有同类功能实现，必须优先复用已有链路和风格，不得另起一套实现。
5. 不得绕开现有主链路随意增加平行逻辑，除非确有必要且保持最小改动。

三、功能范围控制要求

1. 只实现当前提示词明确要求的功能范围。
2. 明确未要求的内容一律不做。
3. 禁止擅自增加以下类型内容，除非提示词明确要求：
- 社区
- 模板市场
- 附件简历
- 报告下载
- 富文本编辑器
- 多版本管理
- 导出 PDF / Word
- 第三个及之后的功能
4. 若发现可以顺手“优化更多内容”，也必须停止，不得超范围实现。

四、代码实现要求

1. 所有实现必须与当前项目结构自然衔接，不破坏现有页面、接口、数据链路和主流程。
2. 新功能应优先复用现有页面、现有接口风格、现有服务层结构、现有公共能力。
3. 数据存储优先采用新增独立表或最小增量结构，禁止无必要修改主链路核心表。
4. 前端实现必须保证不破坏现有页面展示和已有交互逻辑。
5. 后端实现必须保证不破坏现有接口行为和已有业务链路。
6. 若前端未传必要文本，但项目已有可兜底数据源，应优先做兜底处理。
7. 所有新增返回字段、回显逻辑、结果结构必须保持清晰、稳定、可维护。
8. 涉及数据库结构变更（新增表、修改字段、新增索引等）时，必须同步更新 `db/` 和 `server/db/` 目录下的 SQL 脚本，保持两边一致。

五、中文注释与编码要求

1. 所有本轮新增或修改的核心代码，必须补充中文注释。
2. 注释必须使用中文，不能用英文注释替代中文注释。
3. 中文注释必须覆盖关键业务逻辑，而不是只写无意义说明。
4. 中文注释重点覆盖以下内容：
- 关键状态变量
- 提交逻辑
- 回显逻辑
- 复制逻辑
- Controller 接口
- Service 接口与核心实现方法
- AI 调用逻辑
- PDF 文本兜底提取逻辑
- 最近一次记录回显逻辑
- 重要字段与关键数据结构
5. 不要求每一行都写注释，但关键链路必须可读、可维护。
6. 所有包含中文注释的文件必须确保编码正确。
7. 文件保存时必须使用 UTF-8 without BOM 编码；如果项目已有既定编码规范，则必须沿用现有规范并确保中文可正常显示。
8. 严禁出现中文乱码、问号乱码、非法字符、编码错乱、转义异常等问题。
9. 交付前必须自检中文注释显示是否正常。

六、task 与 stage 维护要求

1. 每完成一轮功能开发，必须同步更新 task 文件和 stage 文件。
2. task 文件与 stage 文件必须与实际代码状态保持一致。
3. 后端相关 task 文件和 stage 文件统一放在项目根目录。
4. 前端相关 task 文件和 stage 文件统一放在 frontend 文件夹下。
5. 前后端 task / stage 文件不允许混放。
6. 若本轮同时涉及前端与后端改动，则必须分别在对应目录更新各自的 task / stage 文件。
7. 更新前必须先检查现有 task / stage 的命名方式、内容结构和存放位置，并保持一致，不得另起一套。

七、task 文件内容要求

1. task 文件内容必须使用中文。
2. task 文件必须能够支持后续直接验收，不得写成过度简略的流水账。
3. task 文件至少应包含以下内容：
- 当前任务所属模块
- 前端文件定位
- 后端文件定位
- 本轮修改文件清单
- 前端实现方案
- 后端实现方案
- 数据存储方案
- stage 更新说明
- 编译结果
- 构建结果
- 当前功能验收说明
- 停止，不继续下一个功能
4. 如果本轮为最小修复、兼容修复或仓库遗留问题修复，也必须在 task 文件中明确说明原因、范围和影响。

八、stage 文件更新要求

1. stage 文件必须明确反映当前版本推进状态。
2. 必须清楚标记：
- 已完成且已验收的功能
- 本轮完成状态
- 尚未开始的功能
3. stage 内容不得与实际实现进度不一致。
4. 如果项目已有固定 stage 模板或记录格式，必须严格沿用。

九、验证与构建要求

1. 后端开发完成后，必须执行编译验证。
2. 前端开发完成后，必须执行构建验证。
3. 若本轮涉及前后端，则前后端验证都必须执行。
4. 若出现原项目遗留编译或构建问题，可做最小必要修复，但必须满足以下要求：
- 修复范围最小化
- 不扩展为新功能开发
- 在 task 文件中明确说明该问题属于原仓库遗留问题
- 说明做了什么最小修复
- 说明该修复不属于本轮功能扩展

十、输出与交付要求

1. 完成本轮后，必须按要求输出结果说明，内容应与 task 文件保持一致。
2. 输出内容必须清楚说明本轮改了什么、为什么这样实现、验证是否通过。
3. 完成当前功能后必须立即停止，不得继续开发下一个功能。
4. 未经明确指示，不得开始下一个阶段或下一个功能。

十一、禁止事项

1. 禁止跳过当前功能直接做后续功能。
2. 禁止超范围扩展。
3. 禁止擅自重构大段现有代码。
4. 禁止擅自修改主链路核心数据结构，除非提示词明确允许。
5. 禁止遗漏中文注释要求。
6. 禁止遗漏 task / stage 更新。
7. 禁止把前端和后端的 task / stage 文件放错目录。
8. 禁止交付未编译、未构建验证的代码。
9. 禁止完成后继续推进下一功能。

十二、测试要求

1. 【强制】所有代码新增或修改（包括但不限于 Bug 修复、安全修复、功能开发、重构），必须配套编写测试用例验证修改效果。

2. 测试用例必须覆盖以下场景：
   - 正常路径（功能正常工作）
   - 异常路径（代码防御了什么）
   - 边界条件（空值、越界、并发等）

3. 测试通过标准：
   - 新增测试全部通过
   - 不影响已有测试的通过率
   - 编译无错误

4. 测试用例编写规则：
   - 后端使用 JUnit 5 + Mockito，以 `@Test` + `mock()` 为主的方式，无需启动 Spring 容器
   - 测试类放在对应生产类的 `src/test/java` 同包下
   - 测试方法名使用驼峰命名，以 `should` 开头（如 `shouldRejectPathTraversalUrl`）
   - 测试类名使用 `被测类名 + Test`（如 `PdfTextExtractorTest`）

5. 生成测试用例时，优先考虑使用 test-creator skill 辅助生成，但必须适配本项目 JUnit 5 + Mockito + 中文命名的测试风格。

6. 【强制】一项修改如果通过了编译和构建但未配套测试用例，不算验收通过。验收前提：编译通过 + 所有测试通过 + 测试用例覆盖修改内容。

十三、通用编码规范

1. 【快速失败，大声报错】不要写兜底/降级逻辑，除非任务明确要求。让异常/错误尽早冒泡，不要在业务层内部静默处理错误。

2. 【验证测试】用失败来证明 bug 存在。测试应该能够捕获回归，不要写那种必定通过、什么都没验证的测试。

3. 【注释要求】对外暴露的类型、接口、方法必须加注释说明用途；关键逻辑分支（如空值保护、并发控制、回退策略）必须加功能性注释。

4. 【复用工具函数】优先复用 `common/` 或 `utils/` 里的工具函数。如果通用函数不存在但可以提取复用，先加到工具模块再复用，不要在各处重复实现。

5. 【单元测试目录结构】单元测试严格镜像源码目录结构，每个测试文件只测对应源文件的功能（如 `PdfTextExtractor.java` → `PdfTextExtractorTest.java`）。

6. 【使用源库的类型】始终使用原始库/框架的类型（如 Spring 的 `Result<T>`、JPA 的实体注解），不要创建本地重复类型或把值强转为本地替代类型来绕过类型问题。

7. 【避免无意义的抽象层】如果抽象层没有简化代码或维护真正的边界，就不要加。优先直接调用模块/服务，而不是传宽泛的包装对象。

8. 【不写可推断的返回类型】不要写编译器可以明确推断的冗余类型声明（如方法返回类型、局部变量类型），除非它是公共 API 契约所必需的。

9. 【不提取一次性辅助函数】除非它维护了真正的边界、隐藏了有意义的复杂度、或预期会被复用，否则不要提取。优先内联简单的一次性逻辑。

10. 【简洁直接】写简洁、直接、不绕弯的代码：该报错就报错，该复用就复用，不要过度抽象。

11. 【错误处理统一约束】业务层默认快速失败，让异常尽早冒泡；仅在规则或提示词明确要求的场景（如简历文本兜底、最近一次记录回显）才允许做兜底处理。

12. 【禁止静默失败】禁止空 catch 块、禁止仅 printStackTrace、禁止 catch 后既不记录日志也不向上抛出。所有异常必须有明确的后续处理。

13. 【AI 调用统一封装】所有 AI 调用必须统一走项目现有封装层，禁止在业务代码中直接调用 AI SDK；prompt 必须集中管理，不得散落在各处。

14. 【安全约束】
- 所有用户输入必须校验，禁止拼接 SQL，必须使用参数化查询
- 文件上传/下载必须校验路径遍历攻击
- 敏感数据（如 API Key、密码、Token）不得打印到日志或返回给前端
- 对外接口必须进行身份校验，禁止未授权访问

## 十四、前端 Skills 驱动工作流

涉及前端（`frontend/` 目录）的修改或新建页面，必须严格执行以下流程：

前端skills放在ai-resume\frontend\.claude\skills,涉及前端的请在这里读取skills文件

### 1. 识别任务类型，加载 Skill
| 任务类型 | 必须加载的 Skill |
|---------|----------------|
| 新建页面/新组件 | `ui-ux-pro-max`, `impeccable`, `taste-skill/stitch-skill` |
| 布局调整 | `impeccable/layout`, `impeccable/shape` |
| 色彩/主题 | `impeccable/colorize` |
| 排版优化 | `impeccable/typeset` |
| 动效/动画 | `impeccable/animate`, `impeccable/delight` |
| 响应式适配 | `impeccable/adapt` |
| UI 审查/修复 | `ui-skills/baseline-ui`, `impeccable/audit` |
| 图标 | `better-icons` |
| 无障碍 | `ui-skills/fixing-accessibility` |
| 元数据/SEO | `ui-skills/fixing-metadata` |

### 2. 先理解，再编码
- 使用 `skill` 工具加载对应 skill，仔细阅读其 SKILL.md 全文
- 理解其设计原则、最佳实践和禁止事项
- 将 skill 指导映射到当前任务后，方可进入编码

### 3. 保持项目一致性
- 优先复用项目现有组件、模式、命名风格
- 遵循本文件的所有其他约束
